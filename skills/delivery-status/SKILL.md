# Delivery status reporting

Use current repository, CI, deployment, and owner evidence. Code existence, branch names, and old plans are not proof of delivery state.

For each workstream or component, state the status, supporting evidence, and next action only when one is needed. Use clear labels such as completed, in review/testing, planned, waiting, or blocked; define local terminology if the audience needs it. Do not invent blockers: unknown status is unknown or waiting for evidence.

Show dependencies once and distinguish a blocked source from downstream work that can continue. Keep technical implementation detail out of executive summaries unless it affects risk, cost, timing, or a decision. If a diagram is requested, use an editable, accessible format and ensure it is understandable without colour alone.

Report verified outcomes separately from forecasts or hypotheses. Include an action request only when the recipient must make a decision or provide access.
